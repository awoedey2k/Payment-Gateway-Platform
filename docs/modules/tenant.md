## Tenant status state machine

The JDL status names are authoritative. Mapping to the spec: `PENDING_VERIFICATION` = `PENDING_REVIEW`, `DEACTIVATED` = `CLOSED`; `REJECTED` is the tenant-level outcome of a KYC rejection (the spec only names the KYC status).

```
                        +----------------+
   (created)  --------> | PENDING_REVIEW | ------ KYC rejected --------> REJECTED (terminal)
                        +-------+--------+
        KYC approved (kycStatus=APPROVED)|        \
                                 v        \ sanctions/fraud flag
                        +----------------+ <------ +-----------+
                        |     ACTIVE     |         | SUSPENDED |
                        +-------+--------+ ------> +-----+-----+
                                |   suspend              |  admin remediation (needs kycStatus=APPROVED)
                                |                        v
                                +--- offboard ---> CLOSED (terminal) <--- offboard ---+
```

| From | Allowed to |
| --- | --- |
| `PENDING_REVIEW` | `ACTIVE`, `SUSPENDED`, `REJECTED` |
| `ACTIVE` | `SUSPENDED`, `CLOSED` |
| `SUSPENDED` | `ACTIVE`, `CLOSED` |
| `REJECTED`, `CLOSED` | none (terminal) |

Guards and side effects, all in `TenantLifecycleService` (one transaction, tenant row locked):

- Illegal edge: HTTP 409 `INVALID_TENANT_TRANSITION` (message lists the allowed targets).
- **Any** move to `ACTIVE` requires `kycStatus == APPROVED` (`KYC_NOT_APPROVED`), so neither a direct status call nor suspend-then-reinstate bypasses verification.
- First activation sets `activatedAt`; reinstatement keeps the original value.
- `REJECTED` forces `kycStatus = REJECTED`; `REJECTED` and `CLOSED` revoke every API key permanently.
- `SUSPENDED` keeps the keys but `TenantAccessGuard` refuses their requests (both environments); reinstatement restores them.

What a tenant may do (`TenantAccessGuard`):

| Tenant status | TEST (sandbox) | LIVE |
| --- | --- | --- |
| `ACTIVE` | allowed | allowed |
| `PENDING_REVIEW` | allowed | 403 `TENANT_NOT_VERIFIED` |
| `SUSPENDED` | 403 `TENANT_SUSPENDED` | 403 `TENANT_SUSPENDED` |
| `REJECTED` | 403 `TENANT_REJECTED` | 403 `TENANT_REJECTED` |
| `CLOSED` | 403 `TENANT_CLOSED` | 403 `TENANT_CLOSED` |

The Transaction module (Chunk 4) must call `TenantAccessGuard.assertCanTransact(tenantId, environment)` before creating a charge; that is how a suspended tenant is stopped from starting new transactions. The merchant API-key filter already applies the same decision to every `/api/v1/**` request.

## KYB/KYC onboarding (spec Figure 2.2)

```
POST /api/extended/tenants/{id}/onboarding/screen           (staff, ROLE_ADMIN)

 tx 1  lock tenant; require PENDING_REVIEW + NOT_STARTED; kycStatus = PENDING; snapshot directors
       -- no transaction or lock is held while calling third parties --
       sanctions/PEP screening (business + every director)  ->  signals
       registry cross-reference (registration no. + jurisdiction) -> signals
       KycScoringPolicy: signals -> score 0..100 -> band
 tx 2  lock tenant; require still PENDING; apply outcome
```

| Score | Band | Outcome |
| --- | --- | --- |
| 0-20 | clean | `kycStatus = APPROVED`, tenant `ACTIVE` |
| 21-60 | medium risk | `kycStatus = MANUAL_REVIEW`, tenant stays `PENDING_REVIEW` (Tier-2 human review) |
| 61-100 | critical | `kycStatus = REJECTED`, tenant `REJECTED` |

Manual resolution (`.../onboarding/approve` and `.../onboarding/reject`, body `{"reason": "..."}`) applies only to `PENDING_REVIEW` + `MANUAL_REVIEW`. A rejected tenant (including a sanctions rejection) cannot be approved by hand.

Interleavings (all covered by `OnboardingInterleavingIT`, which holds a screening open between its two transactions):

- If the tenant leaves `PENDING_REVIEW` while its screening is in flight (for example staff suspend it), the result is **discarded** (409 `TENANT_STATUS_CHANGED`, `kycStatus` back to `NOT_STARTED`); an auto-approval never overrides a suspension.
- If the process dies between the two transactions, `kycStatus` stays `PENDING` and retries fail with `KYC_IN_PROGRESS`. Staff recover with `POST /tenants/{id}/onboarding/reset` (body `{"reason"}`); if a screening is in fact still running, its result is discarded (`KYC_STATE_CHANGED`).
- A tenant suspended **before** its first activation can only be closed: it cannot be screened (not `PENDING_REVIEW`) and cannot be reinstated (needs `kycStatus == APPROVED`). The spec has no `SUSPENDED -> PENDING_REVIEW` edge; this is a consequence of following the spec's transitions.

### How the score is computed

The spec gives the bands but not the number, so the score is our own, vendor-independent calculation over discrete findings (`KycSignal`), summed and capped at 100. Weights are configuration (`payment-gateway.tenant.kyc.weights.*`); the defaults below are a proposal to be tuned with compliance:

| Signal | Meaning | Default weight | Alone gives |
| --- | --- | --- | --- |
| `SANCTIONS_HIT` | business or any director on a sanctions list | 70 (floored at 61 regardless of config) | reject |
| `REGISTRY_DISSOLVED` | registry says the business is dissolved | 65 | reject |
| `PEP_HIT` | politically exposed person | 40 | manual review |
| `REGISTRY_NOT_FOUND` | registration number not in the registry | 50 | manual review |
| `NAME_MISMATCH` | registered name differs from the submitted legal name (case/spacing/punctuation-insensitive) | 30 | manual review |
| `REGISTRY_UNAVAILABLE` | registry lookup failed | 30 | manual review |
| `SCREENING_UNAVAILABLE` | sanctions/PEP provider failed | 30 | manual review |
| `NO_DIRECTORS` | nobody on file to screen | 25 | manual review |

Fail-safe rules: a provider that cannot answer is a signal, never a clean result; every default weight exceeds 20, so any single signal at least routes to manual review; only a fully clean check auto-approves.

### Providers

`ComplianceScreeningProvider` (sanctions/PEP) and `BusinessRegistryClient` (registry) are interfaces; no real provider (e.g. ComplyAdvantage, Smile Identity, CAC/Companies House adapters) is provisioned yet, so a **deterministic stub** (`StubKycProvider`, `payment-gateway.tenant.kyc.provider=stub`, the default) is used. Its triggers: a name containing `SANCTIONED` / `PEP`; a registration number starting `DISSOLVED-`, `UNKNOWN-`, `MISMATCH-` or `UNAVAILABLE-`; anything else is clean. **The application refuses to start under the `prod` profile with the stub** (it would auto-approve everyone), or with the development pepper.

The KYC evidence (which signals fired) is logged but not yet persisted; the tamper-evident record belongs to the audit log (Chunk 9).

## API keys (spec §4)

### Format and storage

- Secret key: `sk_live_<64 hex>` / `sk_test_<64 hex>` (256 random bits from `SecureRandom`). Returned **once**, in the response that creates it; never stored, logged (`IssuedApiKey.toString` masks it) or retrievable later.
- Stored on `ApiKey`: `keyPrefix` (first 12 characters, e.g. `sk_live_21f9`, display only; the spec text says "8" but its own example is 12), `keyHash`, `environment`, `isActive`, `issuedAt`, `revokedAt`, `graceExpiresAt`.
- `keyHash = HMAC-SHA-256(pepper, secret)`, hex. The pepper (`payment-gateway.tenant.api-keys.pepper`, supplied via environment in production, at least 32 characters) is never stored with the hashes. A fast keyed hash is appropriate because secrets are high-entropy; a slow password hash would only add per-request latency.
- `keyHash` is unique: authentication is one indexed lookup by hash (the prefix is not used for lookup).

### Rotation sequence (zero downtime)

```
Staff/Dashboard            ApiKeyService                     Database (tenant row locked)
     | 1. rotate(LIVE, 24h) ---> | SELECT ... FOR UPDATE tenant ------------->|
     |                           | usable keys = {A}; require 1 (else 409)    |
     |                           | A.graceExpiresAt = now + 24h               |
     |                           | insert Key B (active) -------------------->|
     | <---- secret B (once) --- |                                            |
     |   ==== window: A and B both authenticate; merchant migrates to B ====  |
     | 2. revoke(A)  ----------> | lock tenant; A.revokedAt = now, isActive=false
     |                           |   (or: grace lapses -> A refused; sweeper flags isActive=false)
```

- A key is *usable* when `isActive`, not revoked, and (`graceExpiresAt` is null or in the future). Lapse is evaluated on every authentication, so a key stops working the instant its grace ends; the periodic sweep (`ApiKeyExpirySweeper`, default every minute) only tidies the flag.
- At most two usable keys per tenant and environment: a rotation while two exist fails with 409 `ROTATION_IN_PROGRESS`; rotating with none usable fails with `NO_ACTIVE_KEY`; issuing when one exists fails with `ACTIVE_KEY_EXISTS`.
- Grace period: `gracePeriodHours` in the request, default 48h, allowed 1h-48h (`GRACE_PERIOD_OUT_OF_RANGE` otherwise).
- Revoke is immediate and idempotent (a second revoke keeps the first `revokedAt`).
- Closing or rejecting a tenant revokes all its keys.
- **LIVE keys are issued on request once the tenant is `ACTIVE`, not automatically at approval.** The spec says live keys are "provisioned automatically", but it also says a secret is shown exactly once; a secret generated during an automatic approval would have nobody to show it to. Activation therefore unlocks LIVE issuance (`POST .../api-keys`), which returns the secret to the requester. TEST keys may be issued while `PENDING_REVIEW` or `ACTIVE`.

### Concurrency

Issue, rotate, revoke, status transitions and KYC decisions all begin with `SELECT ... FOR UPDATE` on the tenant row (`ExtendedCorporateTenantRepository.findByIdForUpdate`), so operations on one tenant are serialised and the invariant above holds; other tenants never block each other. Authentication is read-only and takes no lock. This is proved deterministically in `TenantLockingIT` (hold the lock in one transaction, assert each operation waits, assert authentication does not) and by repeated races in `ConcurrentRotationIT`; both were mutation-checked (removing the lock makes them fail).

## Merchant authentication (`/api/v1/**`)

A second `SecurityFilterChain` (highest precedence, matcher `/api/v1/**`) authenticates `Authorization: Bearer sk_...`; the generated JWT chain is untouched and still handles everything else. A staff JWT is not a merchant credential.

| Situation | Response |
| --- | --- |
| No `Authorization` header | 401 `API_KEY_REQUIRED` (with `WWW-Authenticate: Bearer`) |
| Malformed, unknown, revoked, inactive or grace-expired key | 401 `INVALID_API_KEY` (same body for all, so nothing is revealed about which; with `WWW-Authenticate: Bearer`) |
| Valid key, tenant may not process requests | 403 `TENANT_NOT_VERIFIED` / `TENANT_SUSPENDED` / `TENANT_REJECTED` / `TENANT_CLOSED` |
| Valid key, tenant allowed | request proceeds; principal = `ApiKeyPrincipal(apiKeyId, tenantId, environment)` |

`GET /api/v1/whoami` returns the tenant, key and environment behind a key. `/api/v1/public/**` needs no credentials.

Merchant keys are looked up in the database on every request: revocation and suspension are therefore immediate. Authentication reads a single **projection query** (`ApiKeyAuthRow`: key flags plus the tenant's status), and `TenantAccessGuard` reads the status with a column query. Neither goes through the Hibernate second-level cache, which is per node (Caffeine, 1h TTL) and would let one node miss a suspension or revocation made on another. The stack has no Redis (the spec's Redis cache is a Chunk 4/11 concern); if a per-request cache is added later it must be evicted on revoke and status change.

## Custom domain and locale (spec §5.2)

`GET /api/v1/public/checkout-config` (no credentials) resolves the tenant from the `Host` header against a **verified** `TenantDomain` (case, port and trailing dot ignored) and returns `{customDomain, locale, supportedLocales}`; unknown or unverified hosts get 404. It deliberately omits internal ids.

Locale: `Accept-Language` is matched against the domain's `supportedLocales` (comma-separated, e.g. `en_US,fr_SN`) by quality, then by language ignoring region (`fr-FR` matches `fr_SN`); otherwise `defaultLocale`, then `fallbackLocale`, then `en_US`. A malformed header is ignored.

## Staff API (`/api/extended`, JWT, `ROLE_ADMIN`)

| Method and path | Purpose |
| --- | --- |
| `POST /tenants/{id}/onboarding/screen` | run KYC screening and apply the outcome |
| `POST /tenants/{id}/onboarding/approve` / `reject` | manual review decision, body `{"reason"}` |
| `POST /tenants/{id}/onboarding/reset` | recover a screening stuck in `PENDING`, body `{"reason"}` |
| `POST /tenants/{id}/status` | guarded status transition, body `{"targetStatus","reason"}` |
| `POST /tenants/{id}/api-keys` | issue the first key, body `{"environment"}` (returns the secret once) |
| `POST /tenants/{id}/api-keys/rotate` | rotate, body `{"environment","gracePeriodHours"?}` |
| `POST /api-keys/{keyId}/revoke` | revoke immediately (204) |

Errors are RFC 9457 problem responses carrying a stable `code`.

| Property | Default | Notes |
| --- | --- | --- |
| `payment-gateway.tenant.api-keys.pepper` | dev placeholder | required (32+ chars) under `prod` |
| `payment-gateway.tenant.api-keys.default-grace-period` | `48h` | |
| `payment-gateway.tenant.api-keys.min-grace-period` / `max-grace-period` | `1h` / `48h` | |
| `payment-gateway.tenant.api-keys.expiry-sweep-interval` | `PT1M` | ISO-8601 |
| `payment-gateway.tenant.kyc.provider` | `stub` | refused under `prod` |
| `payment-gateway.tenant.kyc.weights.*` | see table above | each must be 21-100 or the application refuses to start (a weight of 20 or less could auto-approve a finding) |

Startup guard (fails closed for named environments): if any profile is active and none of them is `dev` or `test*` (so `prod`, `staging`, ...), the application refuses to start with the development pepper, a pepper shorter than 32 characters, or `kyc.provider=stub`. **Trade-off:** a run with no active profile at all is treated as development, because JHipster builds always set one (`dev` or `prod`) and the generated Cucumber tests, which cannot be edited, run without any. A deployment that deliberately blanks `spring.profiles.active` would therefore bypass this guard; deployments must set `prod`.

## Decisions recorded (project owner, 2026-09-21)

1. **State machine**: JDL names, spec transitions (this document).
2. **KYC scoring**: own weighted score over provider signals; stub adapter until a provider is chosen.
3. **Key hashing**: HMAC-SHA-256 with server pepper, lookup by unique hash.
4. **Rotation safety**: pessimistic lock on the tenant row.

5. **LIVE keys are issued on request after activation** rather than automatically at approval (spec §2.2): accepted as a deliberate deviation, because the secret is shown once and needs a recipient.
6. **`SUSPENDED -> CLOSED` is kept** as an extension of the spec diagram, so a suspended tenant can be offboarded without being reinstated first.
7. **Generated CRUD is admin-only outside test profiles** (above).
8. **Previously unowned scope assigned** to Chunk 1b and Chunks 4, 7, 9, 10 (above).

Judgement calls made without a question: `TenantDomain.defaultLocale`/`fallbackLocale` added to the JDL; the only merchant-facing endpoints so far are `/api/v1/whoami` and the public checkout config.

## Known gaps and hand-offs

- **Generated CRUD endpoints (security, closed):** the generated `SecurityConfiguration` protects `/api/**` with `authenticated()` only and `/api/register` is open, so any self-registered `ROLE_USER` could otherwise `PUT`/`PATCH`/`DELETE` tenants (skipping the state machine and KYC guard) and API keys (reactivating a revoked key, reading `keyHash`), and write to every other module's tables. `extended.common.config.GeneratedCrudLockdownConfiguration` closes this with a second `SecurityFilterChain` (higher precedence than the generated one) that requires `ROLE_ADMIN` for every generated entity CRUD path: all of `/api/**` except `authenticate`, `register`, `activate`, `account/**`, `admin/**`, `extended/**`, `v1/**` and `users`, so a newly generated entity is locked by default. It is **active in every runtime** (dev, prod, any other profile, or none) and **off only under `test*` profiles**, because the generated integration tests call those endpoints as a plain `ROLE_USER` and cannot be edited; property `payment-gateway.security.restrict-generated-crud` overrides either way. `GeneratedCrudLockdownIT` switches it on and proves it with real signed JWTs (a mutation check confirmed that with it off a plain user gets 200 on the same calls). Consequence: the generated Angular entity screens work for administrators only. The generated ITs never exercise the locked-down path; that is covered by the extended tests.
- **Previously unowned requirements, assigned by the project owner on 2026-09-21** (see the amendment at the top of `TASK_BREAKDOWN.md`): RBAC, tenant users, MFA, self-serve registration and automatic TEST keys go to the new **Chunk 1b**; public `pk_` keys, the `key_id` handle, merchant notifications and white-label go to **Chunk 10**; KYC evidence persistence, compliance-dashboard filing and the Tier-2 review queue go to **Chunk 9**; the settlement-account precondition for `ACTIVE` goes to **Chunk 7**. Until Chunk 1b lands, staff endpoints use the generated JHipster `ROLE_ADMIN`.
- The KYC evidence (which signals fired) is only logged for now; persisting it in the audit log is a Chunk 9 deliverable.
- Acceptance criterion "suspending a tenant blocks new transaction creation" is verified here at the guard and merchant-API level; the check against the real charge endpoint can only be made in Chunk 4. Chunk 4 must call `TenantAccessGuard.assertCanTransact` (or sit behind the `/api/v1/**` chain), add that test, and handle the check-then-act race (a suspension committing between the status read and the charge insert lets one charge through unless the charge transaction re-checks under the tenant lock). This hand-off is now written into Chunk 4's entry in `TASK_BREAKDOWN.md`.
- The generated Liquibase changelogs are regenerated in place (JHipster's default here), so a database that already applied an earlier version of a changelog fails checksum validation. Development databases are ephemeral: drop and recreate.
